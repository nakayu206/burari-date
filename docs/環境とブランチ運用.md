# 環境とブランチ運用ガイド

このプロジェクトにおける「ビルドモード」「Gitブランチ運用」の考え方をまとめたドキュメントです。
kumayokeru-app/tekushare-appでの運用方針を踏襲しています。

---

## 1. Flutterのビルドモード(Debug / Profile / Release)

| モード | 速度 | デバッグ | ホットリロード | 用途 |
|---|---|---|---|---|
| Debug | 遅い | ◎ | ◎ | 開発中 |
| Profile | 速い | △ | ✗ | 性能測定 |
| Release | 最速 | ✗ | ✗ | ユーザーに配布 |

## 2. 環境(Flavor: dev / stg / prod)について

kumayokeru-app/tekushare-appと同様の`main_dev.dart` / `main_stg.dart` / `main_prod.dart`構成を導入済み
(Issue #11)。`lib/main.dart`は引数なし起動時のデフォルトとしてdevに委譲する。

- Android: `productFlavors`(dev/stg/prod)を`android/app/build.gradle.kts`に定義。dev/stgは
  `applicationIdSuffix`で別パッケージ名にし、prodと同一端末に共存インストールできる
- Firebase: プロジェクトは1つ(`burari-date`)を共用し、dev/stg用のパッケージ名を追加登録して
  `google-services.json`に含めている(環境ごとにプロジェクトを分ける対応は必要になったタイミングで検討)
- iOS: xcconfigによるFlavor分けは未対応(Xcode環境が無いため)。iOSリリースが具体化した段階で対応する
- デプロイ自動化: `.github/workflows/deploy-stg.yml`(mainへのpushでstg APKをビルド)/
  `deploy-prod.yml`(`v*.*.*`タグでprod aabをビルド+GitHub Release作成)を導入済み。
  ストアへの自動配信は未設定(開発者アカウント登録後に有効化する)

## 3. ブランチ戦略: GitHub Flow + タグリリース

環境ごとに長命ブランチ(dev/stg/prodブランチ)を作る運用は非推奨。「単一のmainブランチ + CI/CD」
が業界標準([コード規約.md](コード規約.md)参照)。

```
main                    ← これ1本でOK
  ├─ feature/xxx        ← 機能開発(短命)
  └─ fix/xxx             ← バグ修正(短命)
```

```bash
# 1. 機能開発
git checkout -b feature/xxx
git push origin feature/xxx
# → PR作成 → ci.ymlが自動でformat/analyze/testを実行 → レビュー → mainマージ

# 2. 本番リリース(ストア申請が具体化した段階で運用開始)
git checkout main
git pull
git tag v1.0.0
git push origin v1.0.0
```

- 環境別の長命ブランチは作らない
- 全てのPRはレビュー必須(最低1名の承認)
- デプロイ自動化(`.github/workflows/deploy-*.yml`)は導入済み(上記2章参照)
